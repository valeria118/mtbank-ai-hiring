## Архитектура

```
                        ┌──────────────────────┐
   Аудио (чат/URL/API)  │   Pipeline.pipe()    │◄──── REST /analyze (FastAPI)
   ───────────────────► │   / Pipeline.analyze()│
                        └──────────┬───────────┘
                                   │
                     ┌─────────────┴─────────────┐
              ┌──────▼──────┐            ┌───────▼──────────┐
              │ Transcriber │───────────►│    Diarizer      │
              │(faster-     │            │ стерео-каналы /  │
              │ whisper)    │            │ pyannote / паузы │
              └─────────────┘            └───────┬──────────┘
                                                 │
                                transcript: [{speaker,start,end,text}]
                                                 │
               ┌───────────────┬─────────────────┼─────────────────┐
      ┌────────▼───────┐ ┌─────▼────────┐ ┌──────▼───────┐ ┌───────▼──────┐
      │ Классификатор  │ │Агент качества│ │  Compliance  │ │ Суммаризатор │
      │ тема/приоритет │ │ чеклист+балл │ │ правила+LLM  │ │резюме+actions│
      └────────┬───────┘ └─────┬────────┘ └──────┬───────┘ └───────┬──────┘
               └───────────────┴─────────────────┴─────────────────┘
                  AgentOrchestrator.run_all() — asyncio.gather, параллельно
                                                 │
                                  JSON-ответ / markdown-отчёт в чат
```

`pipeline.py` (класс `Pipeline` для OpenWebUI Pipelines) — единая точка правды.
И чат (`pipe()`), и REST (`api/main.py` → `pipeline.analyze()`) вызывают один
и тот же `analyze()`, поэтому поведение не расходится.

Представление при этом разное, намеренно. JSON `/analyze` отдаёт схему из ТЗ
буква в букву. Отчёт в чате — наш формат: подряд идущие реплики одного
говорящего склеены, а к теме и оценке добавлены обоснования агентов
(`reasoning`, `comment`) — именно они объясняют супервайзеру, откуда взялась
оценка. В схеме ТЗ таких полей нет, поэтому в JSON они не попадают.

## Архитектурные решения

**1. Оркестрация — собственный Supervisor, без LangGraph.** Четыре агента
читают один и тот же транскрипт и не зависят от выходов друг друга — графа
зависимостей между ними нет. `asyncio.gather(..., return_exceptions=True)` даёт
параллельный запуск и устойчивость к частичному отказу без лишней зависимости.
LangGraph был бы оправдан при ветвлении, циклах или условных переходах — здесь
их нет. Подробнее — докстринг `agents/orchestrator.py`.

**2. LLM — любая OpenAI-совместимая модель через один клиент**
(`agents/llm_client.py`), настраивается через `.env`
(`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`). По умолчанию Groq
(бесплатный tier, `openai/gpt-oss-120b`, быстрый инференс). Together,
OpenRouter, локальный vLLM или Ollama работают переключением одной переменной,
без правок в коде агентов. Запросы идут с `response_format=json_object` и
`temperature=0`, ретраи — `tenacity`, 3 попытки и только на то, что может
пройти со второй: 429, 5xx, сетевые сбои, невалидный JSON. На 401 и 400
ретраить бессмысленно.

**3. Диаризация — три стратегии, выбор автоматический.** Приоритет у
разделения по стерео-каналам: для контакт-центра это типичный формат записи,
и канал жёстко равен говорящему — точнее любой модели и бесплатно. Для моно:
при заданном `HF_TOKEN` работает `pyannote.audio` (кластеризация по голосу),
иначе резервная эвристика по паузам в аудио. Если pyannote падает на файле, в
режиме `auto` пайплайн тихо откатывается на эвристику; при явном
`DIARIZATION_BACKEND=pyannote` — падает с ошибкой, то есть явный выбор никогда
не подменяется молча.

**4. Compliance — гибрид правил и LLM.** ТЗ требует трёх вещей: запрещённые
фразы, обязательные disclaimers, корректность предложений.

- **Запрещённые формулировки** — детерминированный поиск по подстроке, 100%
  recall на точных фразах. Ищутся только в репликах оператора: клиент,
  сказавший «мне обещали гарантированное одобрение», создаёт не нарушение, а
  повод разобраться.
- **Обязательные раскрытия** — тоже правилом и привязаны к теме: в кредитном
  звонке проверяется, что прозвучали «решение принимает банк», полная ставка и
  оговорка про оферту; где заходит речь о страховании — его добровольность. В
  звонке про блокировку карты ничего из этого не требуется.
- **Тонкие нарушения** (давление, грубость, некорректная подача условий) — на
  LLM, правилом их не выразить.

То, что можно проверить правилом, проверяется правилом — так это устроено и в
реальном комплаенсе.

**5. Отказ агента — не результат проверки.** У упавшего агента значений нет, а
`None` в булевом контексте ложен, поэтому недоступность LLM выглядела бы как
«❌ есть замечания по compliance». Для банка это худший режим отказа:
супервайзер видит нарушение там, где отвалился сервис. Поэтому отказ отделён
явно — в ответе появляется ключ `errors` (только при деградации), в чате
печатается «данные недоступны», `/analyze` отдаёт 502, если не отработал ни
один агент. Деградированный анализ не пишется ни в историю, ни в метрики.

**6. Tools/Actions не реализованы — обоснование.** Термины из критерия взяты
из терминологии OpenWebUI: `Tools` — функции, которые модель вызывает по ходу
разговора, `Actions` — кнопки под сообщением. Сценарий ТЗ «прикрепил аудио →
получил отчёт» решается одним `pipe()`: ветвления нет, модель не выбирает
инструмент. Единственная функция вне этого сценария — тренды по последним
звонкам — сделана текстовой командой (`тренды` в чате) и эндпоинтом
`GET /trends`: работает в любой версии OpenWebUI. ТЗ разрешает отклонение с
обоснованием — это оно.

**7. Valves без секретов.** `LLM_BASE_URL`, `LLM_MODEL`, `WHISPER_MODEL`,
`WHISPER_DEVICE` правятся из админки, `on_valves_updated()` пересобирает
`Transcriber` и `LLMClient` без перезапуска контейнера. `LLM_API_KEY` в валвах
нет намеренно: сервер Pipelines объявляет `GET /{id}/valves` и
`POST /{id}/valves/update` без аутентификации — всё, что туда попало, читается
и переписывается по HTTP. Ключ берётся только из окружения, порт 9099 наружу
не публикуется.

**8. Вложение чата читается с диска, а не по HTTP.**
`/api/v1/files/{id}/content` у OpenWebUI 0.11 требует авторизацию даже при
`WEBUI_AUTH=false` — главный сценарий ТЗ падал на 401. Требовать от
проверяющего выпустить API-ключ руками противоречит «`docker compose up`
поднимает весь стек», поэтому том вложений монтируется в `pipelines` только на
чтение, а файл ищется по id. HTTP остался запасным путём для облака, где
сервисы не делят диск.

## Быстрый старт

```bash
git clone <адрес-репозитория>
cd mtbank-ai-hiring
cp .env.example .env      # впишите LLM_API_KEY
docker compose up --build
```

После старта:

| Сервис | Адрес |
|---|---|
| Чат OpenWebUI — главный сценарий | http://localhost:3000 |
| REST API, Swagger | http://localhost:8080/docs |
| Grafana (бонус) | http://localhost:3001 |
| Потоковая транскрибация (бонус) | http://localhost:8080/realtime |

В чате выберите модель `MTBank Speech Analytics Pipeline` и прикрепите аудио.
Первый старт OpenWebUI занимает несколько минут: он тянет embedding-модель
своего встроенного RAG.

Все порты опубликованы на `127.0.0.1`. Для `9099` это принципиально — маршруты
валвов у сервера Pipelines объявлены без аутентификации (решение 7).

Шаг `cp .env.example .env` можно пропустить: значения имеют дефолты в
`config.py`, а `env_file` помечен необязательным. `.env` нужен ради
`LLM_API_KEY` — без него агенты не смогут обратиться к LLM.

Диаризация по голосу собирается отдельно — она тянет torch:

```bash
docker compose build --build-arg WITH_PYANNOTE=true   # плюс HF_TOKEN в .env
```

Сервис `openwebui-provision` в компоузе — разовый контейнер, который после
старта выключает у модели пайплайна встроенный RAG. Без него любое вложение
уходит в RAG-эмбеддинг, и до пайплайна доезжает не файл, а текстовая выжимка:
анализ не запускается вовсе. Настройка живёт в базе OpenWebUI, из compose её
выставить нельзя — только запросом к API после старта.

### Запуск без Docker

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env
uvicorn api.main:app --reload --port 8080
```

## Живое демо

| Что | Адрес |
|---|---|
| Чат OpenWebUI — главный сценарий | `https://<host>/` |
| REST API | `https://<host>/api/analyze` |
| Swagger | `https://<host>/api/docs` |
| Потоковая транскрибация (бонус) | `https://<host>/api/realtime` |
| Grafana-дашборд (бонус) | `https://<host>/grafana` |

Демо разворачивается на обычной Linux-VM тем же `docker compose` — оверлеем
[`docker-compose.prod.yml`](docker-compose.prod.yml), который добавляет Caddy
(HTTPS от Let's Encrypt автоматически) и ставит `WHISPER_MODEL=medium`.
Порядок и скрипт [`scripts/deploy_vm.sh`](scripts/deploy_vm.sh) — в
[`docs/deployment.md`](docs/deployment.md); там же альтернативы Render и RunPod.

VM выбрана не из экономии: на ней работают все шесть сервисов, включая
бонусные Prometheus и Grafana, которые PaaS-варианты вынуждены выбрасывать.

**Честно про время отклика.** Требование «<60 сек на файл до 5 минут»
относится к критерию «Живое демо», а «модель `medium` или выше» — к критерию
ASR. На CPU выполнить оба нельзя, и выбрана модель. Замер на 4 vCPU:
**запись 66 секунд обрабатывается за 478 секунд**, то есть RTF ≈ 7. Пять минут
аудио на этом железе заняли бы больше получаса. Всё время уходит на
транскрибацию — четыре агента отрабатывают за 5.7 секунды. Для настоящего
«<60 сек» нужен GPU (раздел RunPod в `docs/deployment.md`).

## REST API

```
POST /analyze
Content-Type: multipart/form-data
Body: file=<audio.wav|mp3|ogg>

# или

POST /analyze
Content-Type: application/json
Body: {"url": "https://example.com/call.wav"}
```

Ответ — JSON строго по схеме задания:

```json
{
  "transcript": [
    {"speaker": "Оператор", "start": 0.0, "end": 4.2, "text": "Добрый день, МТБанк..."}
  ],
  "classification": {"topic": "кредиты", "priority": "medium"},
  "quality_score": {
    "total": 78,
    "checklist": {"greeting": true, "need_detection": true, "solution_provided": true, "farewell": false}
  },
  "compliance": {"passed": true, "issues": []},
  "summary": "Клиент обратился по вопросу условий кредита наличными...",
  "action_items": ["Отправить инструкцию по заявке на email клиента"]
}
```

Схема описана в OpenAPI, поэтому на `/docs` эндпоинт вызывается кнопкой
«Try it out» — оба варианта тела.

**Коды ответа.** `400` — файл не распознан как аудио, формат не поддержан,
превышена длительность или в записи нет речи. `502` — не отработал ни один
агент (транскрипт в теле остаётся). При частичном отказе приходит `200` и
дополнительный ключ `errors`; на успешном пути его нет и схема совпадает с ТЗ.

Прочие эндпоинты: `GET /health`, `GET /trends?last=20` (бонус),
`GET /metrics` (бонус), `WS /ws/transcribe` (бонус).

## Бонусные задания

| Бонус | Статус | Где смотреть |
|---|---|---|
| Агент трендов (+5) | ✅ | [`agents/trends.py`](agents/trends.py), `GET /trends`, команда `тренды` в чате |
| Grafana-дашборд (+5) | ✅ | [`deploy/grafana/`](deploy/grafana/), порт `3001`, датасорс и дашборд провижинятся сами |
| Real-time WebSocket (+5) | ⚠️ реализован, порог не выдержан | [`realtime.py`](realtime.py), `WS /ws/transcribe`, страница `GET /realtime` |

Агент трендов работает со сводками нескольких звонков из `storage.py`, а не с
одним транскриптом — поэтому он не проходит через `AgentOrchestrator`. В
потоковом режиме запускается только транскрибация: диаризации и агентам нужен
разговор целиком, а не окно в 2.5 секунды.

Задержка окна `WS /ws/transcribe` на CPU — около 3.8 сек при требовании
«<3 сек». Порог не выдержан, и это отмечено, а не спрятано; на GPU цель
достижима.

## Тесты

```bash
pip install -r requirements.txt -r requirements-dev.txt
pytest -v
```

Или в образе, без локального окружения:

```bash
docker compose build --build-arg WITH_DEV=true && docker compose run --rm api pytest -q
```

**165 тестов, проходят за секунды.** Все обращения к LLM и ASR замоканы, сеть,
ключи и GPU не нужны; `pyannote.audio` тоже не нужен — он импортируется лениво.

- `tests/test_agents.py` — unit-тесты каждого из 4 агентов: fallback
  классификатора, валидация оценки качества (отсутствие `total` — ошибка, а не
  ноль), правила compliance, повтор запроса суммаризатора при выходе за 3–5
  предложений.
- `tests/test_pipeline.py` — интеграционные, включая сквозной прогон
  настоящего `analyze()` с подменёнными ASR и LLM: схема ответа, деградация при
  отказе агента, ASR вне event loop, отказ на тишине, отсутствие секретов в
  валвах.
- `tests/test_api.py` — контракт `POST /analyze` (multipart и JSON), коды 400
  и 502, схемы в OpenAPI.
- `tests/test_diarizer.py` — все три стратегии и автовыбор между ними.
- Остальное: транскрайбер, JSON-логи агентов, SQLite-хранилище, агент трендов,
  Prometheus-метрики, потоковое окно, провижининг, нормализация WER,
  санитайзинг `HF_TOKEN`.

Полный прогон реального аудио через faster-whisper в pytest намеренно не
делается — для этого есть `scripts/run_wer_eval.py`.

## Тестовые данные и WER

`test_data/generate_test_data.py` генерирует аудио из сценария
`docs/sample-dialog.md` через **edge-tts** (голоса `ru-RU-SvetlanaNeural` —
оператор, `ru-RU-DmitryNeural` — клиент).

| Файл | Длит. | Особенность |
|---|---|---|
| `call_dialog_stereo.wav` | 145 с | диалог двух говорящих, стерео (L=Оператор, R=Клиент) |
| `call_dialog_mono.wav` | 145 с | тот же диалог в моно — проверка эвристики |
| `call_dialog_8khz.wav` | 145 с | 8 кГц / pcm_mulaw — телефонное качество |
| `call_complaint_mono/_stereo.wav` | 66 с | жалоба, высокий приоритет, нарушение compliance |
| `short_*.wav` (6 шт.) | 7–14 с | короткие монологи: кредиты, жалоба, переводы, ипотека, карта, приветствие |
| `short_credit_question.mp3` | 10 с | тот же текст — поддержка **MP3** |
| `short_complaint.ogg` | 14 с | тот же текст — поддержка **OGG** |

Требования ТЗ закрыты каждое: 13 файлов при минимуме в 5, файл 8 кГц, диалог
двух говорящих длиннее минуты, все три формата, общая длительность 10.7 минуты
при требуемых пяти.

Уникальной речи при этом 4.4 минуты: `_stereo`/`_mono`/`_8khz` и mp3/ogg — это
варианты одной записи. Они не наполнитель (доказывают форматы, телефонное
качество и две стратегии диаризации на одном содержании), но контентом не
являются. Перекос тоже стоит назвать: шесть из восьми уникальных записей —
монологи, то есть диаризация и чеклист оператора проверяются на двух.

**Эталонные транскрипты** — `*_reference.txt` вида `Спикер: текст`, по одному
на запись; соответствие файлов эталонам задано в `CASES` в
[`scripts/run_wer_eval.py`](scripts/run_wer_eval.py).

| `short_complaint.ogg` | 14 | 26 | 0.0 | 0.0 |

**Средний WER: 4.9%**

MP3 и OGG дают тот же WER, что их WAV-первоисточники — контейнер на точность
не влияет, как и ожидается. Строка `call_dialog_8khz.wav` показывает
деградацию от телефонного качества при том же содержании: 11.1% против 10.1%,
разница небольшая, но направление ожидаемое. Синтетическая речь edge-tts даёт
оптимистичную оценку относительно реальных записей — там нет шума линии,
перебиваний и невнятной дикции.

**Оговорка про времена.** Колонка времени из таблицы убрана намеренно: она
снималась голым `transcribe()`, тогда как рабочий путь идёт через `diarize()`,
и на другой машине. Актуальный замер времени — в разделе «Живое демо»
(RTF ≈ 7). Значения WER и CER от способа замера не зависят.

## Известные ограничения

- **Моно без `HF_TOKEN`** диаризуется эвристикой по паузам, а не по голосу.
  Она ищет паузы ≥1.5 с в самом аудио и изредка путает внутрифразовую паузу TTS
  со сменой говорящего. Стерео-стратегия от этого не зависит.
- **Тестовые данные синтетические** — WER на реальных телефонных записях будет
  выше.
- **Вердикт compliance не воспроизводится побайтово**: `temperature=0` этого не
  гарантирует, на трёх прогонах одного транскрипта `passed` давал False, True,
  False. Детерминированной остаётся правиловая часть — ровно поэтому она и
  вынесена в правила.
- **Обязательные раскрытия распознаются по формулировкам, а не по смыслу** —
  оператор, сказавший то же самое своими словами, даст ложное срабатывание.
- **В потоковом режиме** нет диаризации и агентов, только транскрибация.
- **SQLite** достаточно для прототипа; под нагрузкой реального контакт-центра
  нужен Postgres.
- **История звонков в поставку не входит** (`data/` в `.gitignore`). После
  `docker compose up` база пустая: агент трендов честно ответит, что данных
  нет, а дашборд будет нулевым — прогоните 3–5 файлов, прежде чем показывать
  бонусы.

## Структура репозитория

```
mtbank-ai-hiring/
├── pipeline.py              # OpenWebUI Pipeline — единая точка входа
├── config.py                # pydantic-settings, читает .env
├── storage.py               # SQLite: история анализов
├── metrics.py               # Prometheus-метрики (бонус)
├── realtime.py              # буферизация потоковой транскрибации (бонус)
├── logging_utils.py         # JSON-логи, включая вход/выход агентов
├── agents/                  # llm_client, base, 4 агента, trends, orchestrator
├── asr/                     # transcriber (faster-whisper), diarizer (3 стратегии)
├── api/main.py              # /analyze, /trends, /metrics, /ws/transcribe, /health
├── docker/                  # обёртка, которую сканирует сервер Pipelines
├── deploy/                  # prometheus.yml, Caddyfile, grafana/
├── tests/                   # 13 файлов, 165 тестов
├── test_data/               # 13 аудиофайлов + эталоны + генератор
├── scripts/                 # run_wer_eval, provision_openwebui, deploy_vm.sh
├── docs/                    # sample-dialog.md, deployment.md
├── docker-compose.yml       # api + pipelines + openwebui + provision + prometheus + grafana
├── docker-compose.prod.yml  # оверлей демо: Caddy, HTTPS, medium
├── docker-compose.gpu.yml   # GPU-оверлей
├── Dockerfile               # FastAPI-сервис
├── Dockerfile.pipelines     # сервер OpenWebUI Pipelines
├── render.yaml              # Blueprint для Render
├── requirements*.txt        # основные / dev / pyannote
└── .env.example
```
