## Архитектура

```
                        ┌─────────────────────┐
   Аудио (чат/URL/API)  │                      │
   ───────────────────► │   Pipeline.pipe()    │◄──── REST /analyze (FastAPI)
                        │   / Pipeline.analyze()│
                        └──────────┬───────────┘
                                   │
                     ┌─────────────┴─────────────┐
                     │                            │
              ┌──────▼──────┐            ┌────────▼────────┐
              │ Transcriber │            │    Diarizer      │
              │(faster-     │───────────►│ (стерео-каналы   │
              │ whisper)    │            │  или пауза-эвристика)│
              └─────────────┘            └────────┬─────────┘
                                                   │
                                     transcript: [{speaker,start,end,text}]
                                                   │
                              ┌────────────────────┼────────────────────┐
                              │                     │                    │
                     ┌────────▼───────┐   ┌────────▼───────┐   ┌────────▼────────┐   ┌──────────────┐
                     │  Классификатор │   │Агент качества  │   │   Compliance    │   │ Суммаризатор │
                     │ (тема/приоритет)│   │ (чеклист+балл) │   │ (запрет.фразы + │   │(резюме+action│
                     │                │   │                │   │  LLM-проверка)  │   │   items)     │
                     └────────┬───────┘   └────────┬───────┘   └────────┬────────┘   └───────┬──────┘
                              └─────────────────────┴────────────────────┴────────────────────┘
                                        AgentOrchestrator.run_all() — asyncio.gather (параллельно)
                                                   │
                                        JSON-ответ / markdown-отчёт в чат
```

**Поток данных:** `pipeline.py` (`Pipeline` — класс OpenWebUI Pipeline) — это
единая точка правды. И чат OpenWebUI (`pipe()`), и REST-эндпоинт
(`api/main.py` → `pipeline.analyze()`) вызывают один и тот же `analyze()`,
поэтому анализ в чате и через API один и тот же.

**Представление при этом разное, и намеренно.** JSON `/analyze` отдаёт схему
из ТЗ буква в букву: сегменты транскрипта как есть, без склейки. Отчёт в чате
— формат наш собственный, и в нём: подряд идущие реплики одного говорящего
склеены (иначе «Оператор:» повторяется перед каждым предложением одной
фразы), а к теме и оценке добавлены обоснования агентов (`reasoning`,
`comment`) — модель платит за них токенами на каждом запросе, и это ровно то,
что объясняет супервайзеру, откуда взялась оценка. В схему ТЗ этих полей нет,
поэтому в JSON они не попадают.

## Архитектурные решения (обоснование)

**1. Оркестрация — собственный Supervisor-паттерн, без LangGraph.**
4 агента (классификатор, качество, compliance, суммаризатор) читают один и
тот же транскрипт и не зависят от выходов друг друга — графа зависимостей
между ними нет. `asyncio.gather(..., return_exceptions=True)` даёт
параллельный запуск и устойчивость к частичному отказу (если один агент упал
— остальные результаты не теряются) без лишней зависимости. LangGraph был бы
оправдан при ветвлении/циклах/условных переходах между агентами — например,
для бонусного "агента трендов", анализирующего уже готовые summary
нескольких звонков. Подробнее — комментарий в `agents/orchestrator.py`.

**2. Диаризация — 3 стратегии, выбор автоматический.**
Приоритет отдаётся разделению по стерео-каналам (типично для записи
звонков контакт-центра — раздельные линии на канал), это даёт точную
диаризацию бесплатно и всегда включено, независимо от `DIARIZATION_BACKEND`.
Для моно-записей: если задан `HF_TOKEN` — `pyannote.audio`
speaker-diarization-3.1 (эмбеддинг-кластеризация голоса, точнее на реальных
звонках), иначе — резервная эвристика по длине паузы между репликами (не
требует токена/сети/тяжёлых зависимостей, но менее точна: ориентируется на
паузы, а не на голос, и может ошибаться на длинных монологах без пауз —
известное ограничение). Если pyannote падает на конкретном файле (нет сети,
не приняты условия доступа к gated-модели), в режиме `DIARIZATION_BACKEND=auto`
пайплайн тихо откатывается на эвристику, ошибка только логируется — сервис не
падает целиком из-за одной модели. pyannote тянет за собой torch, поэтому в образ по умолчанию он **не
ставится**: зависимости вынесены в отдельный
[`requirements-pyannote.txt`](requirements-pyannote.txt) и подключаются флагом
сборки `WITH_PYANNOTE=true` (см. «Быстрый старт»). Колёса берутся с CPU-индекса
PyTorch: ~300 МБ вместо 2.7 ГБ, которые тянет тот же torch с PyPI вместе со
всем CUDA-стеком (в распакованном виде это +1.8 ГБ к образу `api`, замерено
на сборке: 1.54 -> 3.33 ГБ). GPU здесь не нужен, на CUDA в этом проекте
считает faster-whisper, а он работает через ctranslate2, не через torch. Как
включить — см. `.env.example` (`WITH_PYANNOTE`, `DIARIZATION_BACKEND`,
`HF_TOKEN`); условия доступа надо принять на **трёх** gated-страницах
HuggingFace, а не на одной — `pyannote.audio` 4.x кроме `speaker-diarization-3.1`
и `segmentation-3.0` тянет ещё PLDA-трансформ из `speaker-diarization-community-1`.

Замер на `call_complaint_mono.wav` (66 сек, CPU, ASR `tiny`): pyannote —
118.6 сек инференса плюс 30.8 сек на загрузку пайплайна, эвристика — 4.6 сек,
то есть разница в 26 раз. Взамен pyannote исправляет ровно тот сбитый участок
в середине звонка, о котором сказано в «Известных ограничениях»: с 44.9 сек
эвристика съезжает на реплику и приписывает клиенту фразы оператора, включая
«гарантированное одобрение» — подсаженное нарушение compliance. На
детерминированное правило это не влияет (поиск запрещённых фраз идёт по всему
тексту), но LLM-проверка compliance и чеклист агента качества читают роли
говорящих. Подробнее — комментарии в `asr/diarizer.py`.

**3. Compliance-агент — гибрид правил и LLM, а не чистый LLM.**
ТЗ требует от него трёх вещей: запрещённые фразы, обязательные disclaimers,
корректность предложений.

- **Запрещённые формулировки** (`FORBIDDEN_PHRASES`) — детерминированный
  поиск по подстроке: 100% recall на точных фразах, не зависящий от
  температуры модели. Ищутся **только в репликах оператора**: клиент,
  сказавший «в отделении мне обещали гарантированное одобрение», создаёт не
  нарушение, а повод разобраться.
- **Обязательные раскрытия** (`REQUIRED_DISCLOSURES`) — тоже правилом, и
  привязаны к теме обращения: в кредитном звонке проверяется, что прозвучали
  «решение о выдаче принимает банк», полная процентная ставка (а не только
  «ставка от») и оговорка про публичную оферту; там, где заходит речь о
  страховании — его добровольность. В звонке про блокировку карты ничего из
  этого не требуется. Тему задаёт весь диалог, а раскрыть обязан оператор —
  поэтому триггер ищется по всему транскрипту, а само раскрытие только в его
  репликах.
- **Тонкие, контекстные нарушения** (давление на клиента, некорректная
  подача условий, грубость) — на LLM, правилом их не выразить.

Это соответствует практике compliance в финансовых организациях: то, что
можно проверить правилом — проверяется правилом. Ограничение правил тоже
стоит назвать честно: раскрытия распознаются по формулировкам, а не по
смыслу, поэтому оператор, сказавший то же самое другими словами, даст ложное
срабатывание. Ловится типовой случай (раскрытия произносят заученной
формулой); нетиповые остаются на LLM-проверке.

**4. LLM — любая OpenAI-совместимая модель через один клиент
(`agents/llm_client.py`)**, настраиваемая через `.env`
(`LLM_BASE_URL`/`LLM_API_KEY`/`LLM_MODEL`). По умолчанию — Groq
(бесплатный tier, `openai/gpt-oss-120b`, быстрый инференс; `llama-3.3-70b-versatile`
Groq снял с обслуживания на момент подготовки решения — см. `.env.example`), но так же
работает с Together/OpenRouter или локальным vLLM/Ollama — переключение
одной переменной окружения, без изменения кода агентов.

**5. Вложение чата читается с диска, а не по HTTP.**
`/api/v1/files/{id}/content` у OpenWebUI 0.11 требует авторизацию **даже при
`WEBUI_AUTH=false`** — на этом главный сценарий ТЗ (загрузка аудио в чат)
падал с 401. Вариант «пусть проверяющий выпустит API-ключ руками» противоречит
требованию «`docker compose up` поднимает весь стек», поэтому том с
вложениями OpenWebUI (`openwebui_data`) монтируется в контейнер `pipelines`
только на чтение, а файл ищется по id (OpenWebUI хранит их как
`{file_id}_{имя}`). HTTP остался запасным путём — он используется, если тома
нет (например, в облаке, где сервисы не делят диск: там `OPENWEBUI_API_KEY`
обязателен, см. [`docs/deployment.md`](docs/deployment.md)).

**6. `response_format={"type": "json_object"}` + `temperature=0` + retry.**
Агенты возвращают структурированные данные, которые парсятся в Python.
JSON-режим API исключает большинство ошибок парсинга; `tenacity`-ретрай на
3 попытки страхует от сетевых сбоев и редких невалидных ответов. Ретраятся не
все ошибки подряд: 401 и 400 со второй попытки успехом не станут, и двенадцать
запросов с экспоненциальными паузами перед пустым отчётом — плохая сделка.
Повторяются 429, 5xx, сетевые сбои и невалидный JSON.

**`temperature=0` — не гарантия детерминизма, и выдавать её за гарантию было
бы неправдой.** На трёх прогонах с побайтово одинаковым транскриптом
compliance дал `passed` = False, True, False, а оценка качества на других
идентичных входах плавала в пределах 80/80/85. Провайдеры не обещают
воспроизводимости при `temperature=0`: на неё влияют батчинг запросов на
стороне провайдера и порядок операций с плавающей точкой. Именно поэтому
проверяемая часть compliance вынесена в правила (пункт 3) — детерминированной
осталась она, а не итоговый булев флаг. Для воспроизводимого вердикта нужно
либо голосование нескольких прогонов, либо seed там, где провайдер его
поддерживает; в этой итерации не сделано.

**7. Tools/Actions не реализованы — и вот почему.**
Термин из формулировки критерия «Pipeline архитектура» взят из терминологии
OpenWebUI: `Tools` — функции, которые модель вызывает по ходу разговора,
`Actions` — кнопки под сообщением. Сценарий ТЗ — «прикрепил аудио → получил
отчёт» — решается одним `pipe()`: вызывать здесь нечего, ветвления нет,
модель не выбирает инструмент. Единственная функция за пределами этого
сценария, тренды по последним звонкам, сделана текстовой командой
(`тренды` / `/trends` в чате) и REST-эндпоинтом `GET /trends`: это работает в
любой версии OpenWebUI и не зависит от того, как конкретная сборка
рендерит Actions. Отдельный `Action`-хендлер добавил бы кнопку и ничего
больше. ТЗ разрешает отклонение с обоснованием — это оно.

**8. Valves — конфигурация из UI, но без секретов.**
`Pipeline.Valves` объявляет `LLM_BASE_URL`, `LLM_MODEL`, `WHISPER_MODEL`,
`WHISPER_DEVICE` — их можно править в админке OpenWebUI, и `on_valves_updated()`
пересобирает `Transcriber` и `LLMClient`, поэтому правка действует сразу, без
перезапуска контейнера.

`LLM_API_KEY` в валвах **нет намеренно**. Сервер Pipelines
(`ghcr.io/open-webui/pipelines:main`) объявляет маршруты `GET /{id}/valves` и
`POST /{id}/valves/update` без `Depends(get_current_user)` — в отличие от
соседних `/models`. Всё, что попало в Valves, читается по HTTP без
авторизации, а через `update` ещё и переписывается. Ключ читается только из
окружения; порт 9099 не публикуется наружу (в `docker-compose.yml` он
привязан к `127.0.0.1`, в `render.yaml` сервис объявлен приватным).

**9. Отказ агента — не результат проверки.**
`asyncio.gather(return_exceptions=True)` сохраняет результаты уцелевших
агентов, но у упавшего значений нет, и `None` в булевом контексте ложен —
поэтому недоступность LLM выглядела бы в отчёте как «❌ есть замечания по
compliance». Для банка это худший возможный режим отказа: супервайзер видит
нарушение там, где просто отвалился сервис. Поэтому отказ отделён от вердикта
явно: в ответе появляется ключ `errors` (только при деградации — на успешном
пути схема остаётся ровно такой, как в ТЗ), в чате печатается «данные
недоступны» и баннер о неполном анализе, `/analyze` отдаёт 502, если не
отработал ни один агент. Деградированный анализ не пишется ни в историю, ни в
метрики: иначе отсутствующая оценка уезжает в гистограмму нулём, а
«комплаенс не отработал» — в счётчик найденных нарушений.

## Быстрый старт

```bash
git clone <адрес-репозитория>
cd mtbank-ai-hiring
cp .env.example .env
# впишите LLM_API_KEY в .env (см. FAQ README задания — бесплатный tier Groq/OpenRouter)

docker compose up --build
```

По умолчанию стенд собирается без `pyannote.audio`: диаризация моно-записей
идёт по эвристике пауз, стерео — по каналам (см. «Архитектурные решения»).
Чтобы собрать с диаризацией по голосу, добавьте в `.env` `WITH_PYANNOTE=true`
и `HF_TOKEN` — сборка станет тяжелее на ~300 МБ:

```bash
docker compose build --build-arg WITH_PYANNOTE=true
docker compose up
```

Шага `cp .env.example .env` можно и не делать: все значения имеют дефолты в
`config.py`, а `env_file` помечен как необязательный — `docker compose up`
поднимает стек сразу после клонирования. `.env` нужен, чтобы вписать
`LLM_API_KEY`: без него агенты не смогут обратиться к LLM.

После старта:
- **OpenWebUI чат:** http://localhost:3000 — загрузите аудио в чат, выберите
  модель `MTBank Speech Analytics Pipeline`.
- **REST API:** http://localhost:8080/docs (Swagger)
- **Pipelines сервер:** http://localhost:9099
- **Grafana-дашборд (бонус):** http://localhost:3001 (анонимный доступ)
- **Потоковая транскрибация (бонус):** http://localhost:8080/realtime

Все порты опубликованы на `127.0.0.1`, а не на всех интерфейсах: из локальной
сети стенд не виден. Для `9099` это принципиально — маршруты валвов у сервера
Pipelines объявлены без аутентификации (см. «Архитектурные решения», пункт 8).

### Запуск без Docker (для разработки)

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
# опционально, только если нужна диаризация по голосу (тянет torch):
# pip install -r requirements-pyannote.txt
cp .env.example .env
uvicorn api.main:app --reload --port 8080
```

`requirements-dev.txt` — pytest, `jiwer` (WER-прогон) и `edge-tts` (синтез
тестового аудио). В прод-образы они не ставятся: собрать образ с ними можно
флагом `docker compose build --build-arg WITH_DEV=true`.

## Живое демо

| Что | Адрес |

| Grafana-дашборд (бонус) | `https://<host>/grafana` |

Демо развёрнуто на обычной Linux-VM тем же `docker compose`, что описан выше,
— оверлеем [`docker-compose.prod.yml`](docker-compose.prod.yml), который
добавляет Caddy (HTTPS от Let's Encrypt автоматически) и ставит
`WHISPER_MODEL=medium`. Порядок развёртывания и скрипт
[`scripts/deploy_vm.sh`](scripts/deploy_vm.sh) — в
[`docs/deployment.md`](docs/deployment.md). Там же два альтернативных пути:
Render (`render.yaml`) и RunPod (`docker-compose.gpu.yml`), если нужен GPU.

VM выбрана не из экономии: на ней работают все шесть сервисов, включая
бонусные Prometheus и Grafana, которые PaaS-варианты вынуждены выбрасывать —
им нужен платный персистентный диск.

**Честно про время отклика.** Требование «<60 сек на файл до 5 мин» относится
к критерию «Живое демо» (5 баллов), а «модель `medium` или выше» — к критерию
ASR (20 баллов). На CPU одновременно выполнить оба нельзя: замеренный RTF
`medium` — около 0.4, то есть пять минут моно превращаются в ~2 минуты
обработки, а стерео — вдвое дольше, потому что каждый канал транскрибируется
отдельно. Выбрана модель. Файлы из `test_data/` короче пяти минут и
укладываются в требование; для настоящего «<60 сек на 5 минут» нужен GPU
(см. раздел RunPod в `docs/deployment.md`).

## REST API

```
POST /analyze
Content-Type: multipart/form-data
Body: file=<audio.wav|mp3|ogg>

# или

POST /analyze
Content-Type: application/json
Body: {"url": "https://example.com/call.wav"}
```

Ответ — JSON строго по схеме из задания (`transcript`, `classification`,
`quality_score`, `compliance`, `summary`, `action_items`). Пример:

```json
{
  "transcript": [
    {"speaker": "Оператор", "start": 0.0, "end": 4.2, "text": "Добрый день, МТБанк..."}
  ],
  "classification": {"topic": "кредиты", "priority": "medium"},
  "quality_score": {
    "total": 78,
    "checklist": {"greeting": true, "need_detection": true, "solution_provided": true, "farewell": false}
  },
  "compliance": {"passed": true, "issues": []},
  "summary": "Клиент обратился по вопросу условий кредита наличными...",
  "action_items": ["Отправить инструкцию по заявке на email клиента"]
}
```

Схема ответа описана в OpenAPI, поэтому на `/docs` эндпоинт можно вызвать
кнопкой «Try it out» — оба варианта тела, файлом и ссылкой.

**Коды ответа.** `400` — файл не распознан как аудио, формат не поддержан,
превышена длительность или в записи нет речи. `502` — не отработал ни один
агент: анализ не выполнен, хотя транскрипт в теле ответа остаётся. При
частичном отказе ответ приходит с `200` и дополнительным ключом `errors`, где
перечислены не отработавшие агенты; пустые значения в их секциях — это отказ
сервиса, а не результат проверки (см. «Архитектурные решения», пункт 9). На
успешном пути ключа `errors` нет и схема совпадает с ТЗ буква в букву.

`GET /health` — проверка живости для healthcheck/мониторинга.

`GET /trends?last=20` — бонус, см. раздел ниже.

`GET /metrics` — экспозиция Prometheus-метрик (бонус).

`WS /ws/transcribe` — потоковая транскрибация (бонус), см. раздел ниже.

## Бонусные задания

| Бонус | Статус | Где смотреть |
|---|---|---|
| Агент трендов (+5) | ✅ | [`agents/trends.py`](agents/trends.py), `GET /trends?last=20`, команда `тренды` в чате OpenWebUI |
| Grafana-дашборд (+5) | ✅ | [`deploy/grafana/`](deploy/grafana/), поднимается вместе со стендом на порту `3001` (провижининг датасорса и дашборда — без ручной настройки) |
| Real-time WebSocket (+5) | ⚠️ реализован, порог не выдержан | [`realtime.py`](realtime.py), `WS /ws/transcribe`, демо-страница `GET /realtime`. Задержка окна на CPU — 3.8 сек при требовании «<3 сек»; см. абзац ниже |

Агент трендов работает не с транскриптом одного звонка, а со сводками
нескольких последних звонков из `storage.py` — архитектурно он не проходит
через `AgentOrchestrator`, потому что у него другой вход (см. докстринг
`agents/orchestrator.py`). В потоковом режиме (WebSocket) запускается только
транскрибация faster-whisper, без диаризации и без 4 агентов — им нужен
разговор целиком, а не окно в 2.5 секунды.

Все три бонуса проверены не только тестами с моками, но и живым прогоном на
поднятом `docker compose up` (реальный `/analyze`, реальное окно
`WS /ws/transcribe` на живом аудио, реальный `/trends` на накопленной
истории).

**Про порог real-time.** Задержка одного окна `WS /ws/transcribe` на CPU —
около 3.8 сек при требовании бонуса «<3 сек». Данные корректны, но порог не
выдержан, и в таблице выше это отмечено, а не спрятано. Цель «<3 сек»
достижима на GPU, где `faster-whisper` работает через `BatchedInferencePipeline`
заметно быстрее. При обрыве соединения хвост буфера дописывается и
отправляется до закрытия сокета — раньше он вычислялся и выбрасывался, то
есть последние слова не показывались никогда.

## Тесты

```bash
pip install -r requirements.txt -r requirements-dev.txt
pytest -v
```

Или в собранном образе, без локального окружения:

```bash
docker compose build --build-arg WITH_DEV=true && docker compose run --rm api pytest -q
```

Все LLM- и ASR-вызовы замоканы (`FakeLLMClient`, подменённая модель
`faster-whisper`) — тесты не требуют сети, API-ключей и GPU, не требуют и
установленного `pyannote.audio` (он импортируется лениво, внутри функции) и
проходят за несколько секунд:

- `tests/test_agents.py` — unit-тесты каждого из 4 агентов: классификатор
  (включая fallback при отсутствующих полях), качество (валидация оценки:
  отсутствие `total` — ошибка агента, а не ноль; диапазон 0-100), compliance
  (детерминированное правило запрещённых фраз, обязательные раскрытия по
  теме, игнорирование фразы, процитированной клиентом), суммаризатор
  (повтор запроса, когда резюме выходит за 3-5 предложений).
- `tests/test_pipeline.py` — интеграционные, включая **сквозной прогон
  настоящего `analyze()`** с подменёнными ASR и LLM: схема ответа на успешном
  пути, деградация при отказе агента (`errors`, отсутствие записи в историю),
  отсутствие тройной транскрибации стерео, ASR вне event loop, отказ на
  тишине и на неподдерживаемом формате, отсутствие секретов в валвах,
  `on_valves_updated()`. Плюс форматирование markdown-отчёта, извлечение
  аудио-ссылки из вложения/URL, лимит длительности, чтение вложения чата с
  тома OpenWebUI.
- `tests/test_api.py` — контракт `POST /analyze` (multipart и JSON `{"url"}`),
  коды 400 и 502, наличие обеих схем тела и схемы ответа в OpenAPI, `/health`.
- `tests/test_logging.py` — JSON-логи входа/выхода агентов: полный вход по
  умолчанию, явная пометка при включённой обрезке, читаемая кириллица,
  логирование и проброс ошибки агента.
- `tests/test_diarizer.py` — все три стратегии диаризации (стерео-каналы,
  pyannote, пауза-эвристика) и автовыбор между ними: и то, что `auto` уходит в
  pyannote только при заданном `HF_TOKEN`, и что при его падении откатывается
  на эвристику молча, а при явном `DIARIZATION_BACKEND=pyannote` — нет.
- `tests/test_transcriber.py` — валидация формата, батчинг на GPU
  (проверяется, что `batch_size` уходит в модель только при `device=cuda`),
  отсев галлюцинаций Whisper по `no_speech_prob` + `avg_logprob`.
- `tests/test_storage.py` — SQLite-хранилище: запись, чтение последних N,
  устойчивость к секции `{"error": ...}` от упавшего агента.
- `tests/test_trends.py` — агент трендов (бонус): пустая история, компактная
  сводка в промпте вместо сырых транскриптов, дефолты при неполном ответе LLM.
- `tests/test_metrics.py` — Prometheus-метрики (бонус): счётчики по теме/
  приоритету, гистограмма quality_score, отдельный счётчик деградации,
  экспортёр для контейнера pipelines, эндпоинт `/metrics`.
- `tests/test_realtime.py` — буферизация окна потоковой транскрибации (бонус):
  накопление до полного окна, сброс после транскрибации, абсолютные таймкоды,
  `flush()` хвоста при отключении.
- `tests/test_provision.py` — провижининг OpenWebUI (выключение встроенного
  RAG для модели пайплайна).
- `tests/test_wer_eval.py` — нормализация текста перед подсчётом WER и
  точность атрибуции ролей по выравниванию слов.
- `tests/test_config.py` — санитайзинг `HF_TOKEN`: значение, не похожее на
  токен (незаполненный плейсхолдер, кириллица, забытые кавычки), считается
  отсутствием токена и вычищается из окружения. Иначе оно ломает не
  диаризацию, ради которой задано, а транскрибацию: `huggingface_hub` берёт
  `HF_TOKEN` из окружения для любой загрузки, включая модель faster-whisper.

Полный end-to-end прогон реального аудио через faster-whisper в pytest
намеренно не делается (тяжёлая модель — секунды-десятки секунд на CPU) — для
этого есть `scripts/run_wer_eval.py`, запускаемый отдельно.

сценария `docs/sample-dialog.md` через **edge-tts** (голоса Microsoft

| `short_complaint.wav` | 14 сек | монолог клиента, жалоба |

| `short_mortgage_question.wav` | 8 сек | монолог клиента, ипотека |
| `short_card_block.wav` | 7 сек | монолог клиента, блокировка карты |
| `short_operator_greeting_variant.wav` | 7 сек | монолог оператора, вариант приветствия |
| `short_credit_question.mp3` | 10 сек | форматный вариант `short_credit_question.wav` (тот же текст/эталон) — доказывает поддержку **MP3** |
| `short_complaint.ogg` | 14 сек | форматный вариант `short_complaint.wav` (тот же текст/эталон) — доказывает поддержку **OGG** |

**Объём — два разных числа, и путать их не нужно.**

- **Общая длительность набора: 10.7 минуты** (13 файлов). Именно её и
  требует ТЗ («общая длительность — не менее 5 минут»), и требование закрыто
  вдвое.
- **Уникальной речи: 4.4 минуты** (8 разных записей: два диалога и шесть
  коротких монологов). Остальное — тот же текст в другом контейнере, другом
  sample rate или другой канальности: `_stereo`/`_mono`/`_8khz` варианты
  диалогов и mp3/ogg-варианты коротких файлов.

Эти пять «дублей» — не наполнитель. Форматные варианты доказывают поддержку
MP3 и OGG, `_8khz` — телефонное качество, `_stereo`/`_mono` — две разные
стратегии диаризации на одном и том же содержании, что и делает сравнение
осмысленным. Но контентом они не являются, и выдавать их за него было бы
неправдой.

Отдельные требования ТЗ закрыты каждое: 8kHz-файл (`call_dialog_8khz.wav`),
диалог двух говорящих длительностью более минуты (`call_dialog_stereo.wav`,
2.4 мин), все три формата — WAV/MP3/OGG, файлов 13 при требуемых 5.

**Эталонные транскрипты** — `*_reference.txt` вида `Спикер: текст`, по одному
на каждую *запись*, а не на каждый файл: варианты одной записи ссылаются на
общий эталон (`call_dialog_stereo.wav`, `_mono`, `_8khz` → один
`call_dialog_reference.txt`). Соответствие файла эталону задано в
`CASES` в [`scripts/run_wer_eval.py`](scripts/run_wer_eval.py).

**Перекос набора, который стоит назвать.** Шесть из восьми уникальных записей
— монологи одного говорящего. На них не нагружаются ни диаризация, ни
чеклист оператора, то есть ровно то, за что дают 20 баллов, проверяется на
двух записях из восьми (зато в шести файловых вариантах, включая стерео и
8 кГц). Формальные требования ТЗ это закрывает; набор, нагружающий
диаризацию по-настоящему, потребовал бы ещё двух-трёх диалогов.

телефонных записей (нет шума линии, перебиваний, невнятной дикции). Строка

железе транскрибируется не за требуемые ТЗ <60 сек, а ближе к 120-130 сек —
батчинг `faster-whisper` 1.1 ускоряет только GPU-режим (`device=cuda`), на CPU
`batch_size` не применяется. Требование «<60 сек» относится к критерию «Живое
демо» (5 баллов), требование `medium` — к критерию ASR (20 баллов), поэтому
в деплое стоит `medium`: см. раздел «Живое демо».

`call_dialog_stereo.wav` на идентичном содержании) включала ленивую загрузку

## Известные ограничения

- **Диаризация моно-записей без `HF_TOKEN`** — резервная пауза-эвристика
  (не speaker-embedding). См. обоснование выше. Стерео-стратегия
  (приоритетная, типичный формат записи контакт-центра) — надёжная: канал
  жёстко = спикер, от `HF_TOKEN` не зависит. Моно-эвристика ищет паузы ≥1.5с
  в самом аудио (`asr/diarizer.py`, `TURN_SILENCE_MS`) и на многострочных
  репликах изредка путает внутрифразовую паузу TTS с реальной сменой
  говорящего — на `call_complaint_mono.wav` это даёт короткий (2-3 реплики)
  сбитый участок посередине звонка, который сам выправляется дальше. Для
  моно-записей реальных звонков рекомендуется собрать стенд с
  `WITH_PYANNOTE=true` и задать `HF_TOKEN` — тогда работает `pyannote.audio`
  (диаризация по голосу, а не по паузам), см. `.env.example`. В образе по
  умолчанию его нет: в режиме `auto` пайплайн тихо остаётся на эвристике, в
  режиме `pyannote` — падает с ошибкой импорта, то есть явный выбор бэкенда
  никогда не подменяется молча.
- **Тестовые данные синтетические** (edge-tts) — WER на реальных телефонных
  записях будет выше, чем в таблице ниже; синтетическая речь чище живого
  звонка (без шума линии, перебиваний, невнятной дикции).
- **В потоковом режиме (WebSocket)** не запускаются диаризация и 4 агента —
  только транскрибация. Обоснование — в разделе «Бонусные задания».
- **SQLite как хранилище результатов** — достаточно для прототипа и для
  агента трендов/дашборда в рамках тестового задания; под нагрузкой
  реального контакт-центра нужна полноценная БД с конкурентным доступом
  (Postgres) вместо файловой SQLite.
- **Вердикт compliance не воспроизводится побайтово** на повторном прогоне
  одного и того же транскрипта — `temperature=0` этого не гарантирует.
  Детерминированной остаётся правиловая часть (запрещённые фразы и
  обязательные раскрытия), LLM-часть плавает. Подробнее и что с этим делать —
  «Архитектурные решения», пункт 6.
- **Обязательные раскрытия распознаются по формулировкам, а не по смыслу** —
  оператор, сказавший то же самое своими словами, даст ложное срабатывание
  правила. См. «Архитектурные решения», пункт 3.
- **История звонков в репозиторий не попадает** — `data/` в `.gitignore`, и
  `.dockerignore` тоже исключает её из контекста сборки. После
  `docker compose up` база пустая: агент трендов честно ответит, что данных
  нет, а дашборд Grafana будет нулевым, пока не прогнать несколько анализов.
  Это правильно (чужая SQLite с чужими прогонами в поставке никому не нужна),
  но означает лишний шаг перед демонстрацией бонусов: прогнать 3–5 файлов из
  `test_data/` через `/analyze` или через чат, и только потом показывать
  тренды и дашборд.
- **Тесты не покрывают** HTTP-уровень `/trends` и `/ws/transcribe` (покрыта
  логика под ними) и повторные попытки `LLMClient.complete_json`.

### Провижининг OpenWebUI — зачем отдельный сервис

`openwebui-provision` в компоузе — разовый контейнер, который после старта
чата выключает у модели пайплайна встроенный RAG. Без него главный сценарий
ТЗ ломается неочевидным образом: **любое вложение в чате OpenWebUI по
умолчанию уходит в RAG-эмбеддинг**, а до пайплайна доезжает не файл, а
текстовая выжимка из него. Для аудио это означает, что анализ не запускается
вовсе, а модель отвечает по пустому контексту.

Настройка живёт в базе OpenWebUI, а не в переменной окружения, поэтому
выставить её из `docker-compose.yml` нельзя — только запросом к API после
старта. Сервис делает ровно это и завершается; если он не отработал, стек
поднимается, но чат деградирует до RAG-инъекции. Код —
[`scripts/provision_openwebui.py`](scripts/provision_openwebui.py), тесты —
`tests/test_provision.py`.
